## 執筆インターフェース

### 日ページからのポスト投稿・インライン編集（メイン）

日々の執筆は、確認サーバ（`npm run dev`）で日ページを開いたまま、**Twitter（X）のように短いテキストや写真を即座にポストする** 運用を前提に設計されています。思いついたことをその場で書き留め、過去の記述もその場で直せます。

- **新規投稿**: 右下の **＋** ボタンで起動。開いた時刻が見出しに入り、サーバ時計の分のファイル（`HH-MM.md`）へ書き込みます。同じ分に再度投稿した場合は空行を挟んで追記されます。
- **日付・時刻の調整**: 見出しの日時をクリックして変更可能。変更した要素のみが書き込み先パスに反映され、変更しなかった要素は現在時刻が維持されます。
- **既存ブロックの編集・削除**: 時刻ブロック右端の「編集」で内容を置き換え可能。「削除」は2度押しで実行。
- **写真選択**: 端末の写真ライブラリ（iOS ではカメラ直接撮影も可）から R2 に直接アップロード。
- **同期トースト**: 編集・投稿後は左下に「同期」ボタン付きトーストが出現。明示的に押すまで自動デプロイは行われません。
- **ショートカット**: **⌘Enter**（投稿・保存）、**⌘S**（保存）、**Esc**（閉じる）。ダイアログ展開中はサイト側のキーバインド（`/` や `d`）が無効化されます。
- **レスポンシブ**: 幅 681px 未満ではボトムシート、681px 以上では中央モーダルダイアログとして展開されます。

### 安全設計とネットワーク構成

- **`site/` を汚さない動的インジェクション**:
  日ページ上の編集 UI（`scripts/edit.js`, `scripts/edit.css`）は、ビルド成果物である `site/` には一切書き出されません。確認サーバ（`npm run dev`）が日ページの HTML を返す際、リクエストが **loopback（127.0.0.1 / ::1）からのアクセスである場合のみ**、`</body>` 直前に動的にスクリプトタグを差し込みます。これにより、誤った設定でエディタ機能を含んだ HTML が公開環境へデプロイされる事故を防止しています。
- **モバイル端末からのアクセス**:
  スマートフォンからインライン編集を利用する場合、端末から開発マシンの loopback に届く経路（`tailscale serve` など。tailscaled が localhost 宛に中継する仕組み）が必要です。Cloudflare Tunnel（Funnel）等でインターネットに直接露出させる場合は、認証レイヤーを別途追加する必要があります。

### Web エディタ（`/_write` / 補助機能）

長文の推敲や過去記事の一覧確認用として、3 ペイン構成のエディタも提供されています。

```
http://localhost:8888/_write
```

- **3ペイン構成**: 左が過去の記事一覧、中央が本文入力、右がプレビュー。
- **プレビュー同期**: 実際に生成された日ページを表示。保存時は再ビルド完了を待ってからレスポンスを返すため、保存と同時に最新状態が描画されます。
- **ファイルパス連動**: 上部バーの日付と時刻がそのまま書き込み先（`content/YYYY/MM/DD/HH-MM.md`）になります。
  - **いま**: 現在の日付・時刻をセット。
  - **新規**: 入力欄を空にして新しい時刻ブロックを開始。
  - 日付・時刻を変更しても書きかけの本文は消えず、保存先パスのみが移動します（移動先に既存ファイルがある場合は警告を表示）。
  - 本文欄が空の状態で日付・時刻を変更した場合は、該当時刻の既存ファイルを読み込みます。
- **ショートカット & 操作**:
  - 保存: **⌘S**（Ctrl+S）。削除: 2度押し。
  - 写真: ドラッグ＆ドロップまたはペーストで R2 に自動アップロードされ、Markdown 記法が本文に挿入されます。
  - 未保存の変更がある状態で他記事を開く、または同期しようとすると確認の停止が入ります。
- **同期**: 画面上の「同期」ボタンを押すと、ビルドおよび Cloudflare へのデプロイ（`npm run deploy` 相当）が実行され、結果が画面上部にリアルタイム表示されます。

## 写真とストレージ（Cloudflare R2）

### 静的アセット制約と外部化

Cloudflare Workers の Static Assets にはファイル数上限（20,000 件）が存在します。日々の写真を静的ファイルとしてリポジトリに蓄積していくと上限を圧迫するため、エディタから投入された写真はすべて Cloudflare R2 に保存します。

### 命名規則とメタデータ

R2 バケット内はディレクトリ階層を持たず、アップロード日時ベースのフラットな構造です。

```
img/2026-08-30-14-59-13.png        ← サーバ時計（YYYY-MM-DD-HH-MM-SS）
img/2026-08-30-14-59-13-k3f.png    ← 同一秒内に複数アップロードされた場合のみ付与されるランダムサフィックス
```

ファイル名は記事の日付ではなく「アップロードされた実時間」で固定されるため、後から Markdown 側の時刻ブロックや日付を変更しても画像 URL が破損することはありません。また、記事側で削除された画像のガベージコレクションは行いません（必要時は全 Markdown ファイルの参照と R2 バケット一覧の差分抽出で対応）。

### 寸法計測とレイアウトシフト（CLS）対策

HTML 出力時、すべての画像タグに `width` / `height` / `aspect-ratio` をインラインスタイルとして付与し、画像読み込み中のレイアウト崩れ（Cumulative Layout Shift）を防止しています。
- **R2 画像**: アップロード時に寸法を計測し、`.cache/imagesize.json` にキャッシュ。ビルド時にネットワーク通信は発生しません。
- **外部 URL 画像**: ビルド時に初回のみ画像をダウンロードして計測し、同キャッシュに保存。
- **手元のローカル画像**: 日ディレクトリ配下（`content/YYYY/MM/DD/img/` 等）のファイルを直接読み取って計測（ビルド成果物 `site/` にコピーされます）。

### バケット設定

- **公開バケット（画像用）**:
  R2 バケットにカスタムドメイン（例: `img.example.com`）を紐付けます。バケット全体が公開されるため、写真以外の機密ファイルは格納しません。
- **`.env` 設定**:
  ```sh
  HIBI_R2_BUCKET=hibi                  # 写真用バケット名
  HIBI_R2_URL=https://img.example.com  # 公開 URL プレフィックス
  ```

## フロントエンド設計

### クライアントサイド検索

- **インデックス生成**: ビルド時に全記事のテキスト（本文・引用・箇条書き・追記・画像キャプション・OGP情報・X ポスト本文）を `/search.json`（新着順）に出力。
- **ブラウザ内検索**: 初回展開時のみ `/search.json` を非同期フェッチし、メモリ内でインクリメンタルに絞り込み。
- **正規化**: 全角/半角、大文字/小文字、ひらがな/カタカナを同一視。半角空白区切りで AND 検索。
- **キー操作**: `/` または `⌘K` で検索窓を開き、`↑` `↓` で選択、`Enter` で該当日の記事へ遷移、`Esc` で閉じる。

### 日付ジャンプダイアログ

- **軽量データ**: カレンダー生成のため、記事が存在する日付のリストのみを持つ軽量な `/days.json` を使用（`/search.json` は使用しない）。
- **キー操作**: `d` キーで今いる月のカレンダーを表示。記述のある日のみフォーカス可能（`Tab` でスキップ移動、`←` `→` で月送り）。
- **月判定**: トップページ（`/`）は最新日ページのコピーであるため、パス名ではなく `<link rel="canonical">` を参照して現在の日付・月を特定します。

### View Transitions（画面遷移）

同一ドメイン内のページ遷移（月一覧 ⇔ 日ページ、日ページ内の時刻アンカージャンプ）において、要素の位置と形状を自然に繋ぐ View Transitions API を採用しています。

- **モーフィング対象**: 日付（`.datelink`）、時刻（`.times`）、本文（`.body`）の 3 要素に `view-transition-name` を動的付与。両ページで共通のレイアウトを持つため、シームレスに位置がアニメーションします。その他全体はクロスフェード。
- **スクロール位置の補正**: 日ページから「一覧へ」で戻る際、対象の日が画面外にあるとアニメーションが成立しないため、`assets/vt.js` が該当日の位置までスクロール位置を調整してからトランジションを開始します。
- **CSS 先頭配置の必然性**: `@view-transition` は `assets/style.css` の最先頭に宣言されています。後方に配置すると、遷移先ページの初期描画完了までにスタイル解決が間に合わず、トランジション自体がブラウザによってスキップされるためです。
- **`defer` を使わない理由**: `assets/vt.js` は `pagereveal` イベントへの登録タイミングを担保するため、`defer` 属性を付けずに同期読み込みさせています。

### レスポンシブとレイアウト設計

- **ブレークポイント**: `681px`。
  - **681px 以上（2段組）**: 左側に日付と時刻のメタ情報（`.meta`）および「一覧へ」ボタンが固定表示（`position: sticky`）。本文をスクロールしても左右の視覚的間隔（`--rail-top`, `--rail-gap`）を均一に保ちます。
  - **681px 未満（1段組）**: 日付と時刻が本文の上に積み重なる自然なフローレイアウトへ変化。
- **並び順**: 暦順（過去から未来）を徹底。月一覧は 1 日から末日に向かって降順ではなく昇順、日・月の前後の移動も左が過去・右が未来です（新着降順になるのは RSS の `/feed.xml` と `/search.json` のみ）。

## グラフィックとデザイン幾何学

### ファビコン（`favicon.svg`）の幾何学

ファビコンはサイトの 2 段組レイアウトを抽象化した形状です。左が上辺で止まる日付の柱、右が下辺を突き抜ける本文の柱。中央を横切る細い罫線が左右の壁に接することで「日」の文字を形成します。

- **角丸 `rx=5.5` の幾何学的導出**:
  外枠（板）のサイズは 32×32。板の下辺が直線として維持される限界は `x = 32 - rx` までで、それ以降は角の円弧に入ります。右側の本文の柱の右端座標は正確に `26.5` です。
  $$32 - 5.5 = 26.5$$
  もし `rx` を 5.5 より大きくすると、下へ突き抜ける柱の右端が角の円弧によって斜めに削り取られ、下辺の角に先細りの白い楔状ノイズが発生します（`rx=7` の場合、512px レンダリング時に 16px 相当の欠損が発生）。
- **罫線の 1px オーバーシュート**:
  中央の罫線は左右の柱よりも幅を 1px ずつ広げて描画されています（柱の幅 `15 → 26.5` に対し、罫線は `14 → 27.5`）。
  両端を柱の座標と完全に一致させると、アンチエイリアス処理によって境界ピクセルのアルファ値が不完全になり、黒地の中に消しきれなかった白が縦のゴースト線（180px レンダリングで R=38 vs 23）として浮き出ます。外側の地色と同じ黒でわずかにオーバーラップさせることで、サブピクセルの白浮きを完全に防止しています。

### iOS ホーム画面用アイコン（`apple-touch-icon.png`）

```sh
node scripts/icon.mjs   # assets/favicon.svg → assets/apple-touch-icon.png (180x180)
```

- iOS の Web クリップは SVG ファビコンを解釈しないため、PNG 画像（180×180）を生成します。
- `sharp-cli` をリポジトリの依存に含めず、`npx` 経由でオンデマンド実行することで、リポジトリの `node_modules` ゼロ（ゼロ依存）を維持しています。
- **角丸の除去**: SVG 内の外枠角丸を PNG 変換時に除外しています。iOS 側がシステム標準の角丸（約 22.4%）でマスク処理を行うため、画像側であらかじめ角丸（17.2%）を付けておくと四隅に黒い余白ノイズが発生するためです。

### OGP 画像（`og.png`）の設計

```sh
node scripts/og.mjs   # assets/og.png (1200x630)
```

- **写真のある日**: 記事内の 1 枚目の写真を採用。
- **写真のない日・一覧・404**: `assets/og.png`（ファビコンの印を拡大配置したグラフィック）を使用。
- **地色を墨（黒）にする理由**: Slack や X などの白い背景にプレビューカードが置かれた際、白地の板だと境界が溶けて消失するため、外側を黒で塗り潰すことで枠組みを際立たせています。
- **文字を排した理由**: SVG ラスタライザ（sharp / resvg）は実行環境のシステムフォントしか解釈できず、サイトで使用している Shippori Mincho や Roboto Mono が意図しない代替フォントに化けるリスクを避けるため、文字を一切入れないシンボルマークのみの構成としています。

### トップページ（`/`）のメタデータ制御

トップページ（`/`）は内容としては最新の日ページの完全な複製ですが、以下のメタデータ上書きを行っています。

- `og:type`: `website`
- `og:title`: サイト名（記事日付ではなくサイト自体の看板として展開させるため）
- `og:image`: 写真があっても `assets/og.png` を強制
- **`canonical` を維持する理由**:
  `<link rel="canonical">` だけは最新日ページの URL を維持しています。`assets/jump.js` や `scripts/edit.js` が「今開いている日」を canonical から取得する設計になっているため、これを変更するとトップページからのインライン編集や日付ジャンプ機能が破損します。

## インフラと運用

### Cloudflare Workers Static Assets への直接デプロイ

`scripts/deploy.mjs` は Cloudflare API を直接叩き、`site/` の生成ファイルを Static Assets にアップロードします。

- **ビルド枠の節約**: Cloudflare 側でビルドを走らせないため、無料枠（月 500 回）の制限を受けず、1 日に何度でもデプロイ可能です。
- **差分転送**: ファイルのハッシュ値を比較し、変更のあったファイルのみを転送するため、通常は数秒で完了します。
- **ルーティング設定**: `/YYYY/MM/DD` から `/YYYY/MM/DD/` へのトレイリングスラッシュ解決や 404 リダイレクト設定は、デプロイ時に Worker のアセット設定（`html_handling`, `not_found_handling`）としてマニフェスト内で直接指定しています。

### R2 への双方向バックアップ

記事ファイル群（`content/`）はプライベートな記録を含むため Git 管理外（`.gitignore`）となっています。そのため、デプロイと連動して Cloudflare R2 に自動バックアップを行います。

```sh
npm run backup                            # 手元 content/ の変更差分を R2 へアップロード
node scripts/backup.mjs --dry-run         # 送信対象の確認
node scripts/backup.mjs --pull            # R2 から手元 content/ へ復元（新規マシンセットアップ時）
node scripts/backup.mjs --pull --dry-run  # 復元対象の確認
```

- **独立バケット**: 画像用バケット（公開）とは別に、非公開の専用バケット（`HIBI_R2_BACKUP_BUCKET`）に格納。
- **削除保護**: 手元でファイルを削除しても、R2 側のバックアップからは自動削除しません（誤削除時の救済）。
- **`--pull`**: 新しい PC で作業を再開する際、R2 を正としてローカルの `content/` を復元します。

### キャッシュ構造

外部通信や高負荷な解析結果はすべて `.cache/` に永続化され、2 回目以降のビルド時間をミリ秒単位に抑えています。

- `.cache/imagesize.json`: 画像の縦横寸法・アスペクト比
- `.cache/linkcard.json`: `@link` で指定された OGP の取得結果
- `.cache/xpost.json`: `@x`（Twitter/X）の oEmbed 取得結果（埋め込みが消えても静的カードとして残すためのデータ）
